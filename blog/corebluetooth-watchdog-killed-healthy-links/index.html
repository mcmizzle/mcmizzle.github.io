My Core Bluetooth watchdog tore down five healthy links in four minutes

Kevin McMahon · November 17, 2026

Five link teardowns in four minutes, and the peripheral was acknowledging every write while it happened. The app would reconnect, work for half a minute, and drop again. Nothing was wrong with the radio, the peripheral, or the thresholds I had picked. The watchdog I wrote to notice a dead link was killing live ones, and it did it faster the busier the app got.

That last part is the fingerprint. If your Bluetooth LE drops track your own traffic, the rest of this will probably look familiar.

Why there was a watchdog at all

The app drives a BLE controller for a piece of display hardware. Almost all the traffic goes one way: writes of absolute state, as often as the state changes. The device sends very little back.

Those writes go out unacknowledged, so they never queue behind a reply. Apple is blunt about what that costs. The documentation for CBCharacteristicWriteType.withoutResponse describes it as a write "without any response from the peripheral to indicate whether the write was successful," and adds: "You receive no notification if writing to a characteristic value fails with this write type."

So my send function cannot fail. Not rarely — there is no failure path in it. A powered-off device and a working one are the same thing from the writing side.

In plain English: what is a write without a response?

Bluetooth LE lets you send a value to a device two ways. One waits for the device to confirm it arrived. The other fires and forgets, which is faster and keeps a stream of updates flowing, at the price of never learning whether anything was received.

Core Bluetooth will tell you when a link drops. It cannot tell you about a device that holds the link open and stops doing its job, because from the system's point of view nothing is wrong. If I wanted to know that, I had to ask.

The first version watched the wrong layer

The device answers each keepalive with a status frame, so an established link produces inbound traffic every four seconds. Silence meant it was gone. Three missed in a row, twelve seconds, tear the link down and rebuild it.

Then a capture falsified that. The device went mute on its status channel for 54 seconds — no status frames, no command acknowledgements, no answer to a full re-query sweep — while the link stayed up, the ATT layer answered every write, and the hardware visibly obeyed both the command before the silence and the one after it.

It was executing commands the entire time it was silent. My rule would have torn down a working link after twelve seconds, and would have kept doing it: the same device later went mute for two minutes while the display followed every write.

The signal that did track reality

One layer down from the application: the ATT write acknowledgement. Core Bluetooth only reports one for a write you sent asking for it, and through the whole mute those kept coming back on time.

In plain English: what is ATT?

The low-level protocol underneath everything Core Bluetooth does. Your app asks for a value or sets one, and ATT is the layer that carries the request and the reply. The device's own software has to be running to answer at that level, which is why an answer there means something.

Worth being precise about one detail, because it is the useful half: an error response counts. This firmware answers every write with an ATT error and acts on the write regardless. For liveness that is fine. The question is not whether the write succeeded, it is whether anything on the other end is still well enough to form a reply and send it.

That costs exactly one thing, and it is the thing this whole post is about. The delegate callback that reports a write only fires for the acknowledged write type, so the keepalive had to go out .withResponse purely to produce something I could time. Only the keepalive. State writes stayed unacknowledged.

And then it killed five healthy links

Three decisions, each defensible on its own:

  • Liveness is measured on ATT acknowledgements.
  • Only the keepalive is written with a response, so it is the only thing that produces one.
  • The keepalive goes out after four seconds of write idleness.

A rehearsal run writing every 1.4 seconds never went four seconds without a write. So the keepalive never went out. So nothing was acknowledged. So there was no evidence of life, and twelve seconds later the watchdog tore down the link it had just blinded itself to.

The busier the link, the faster it fired. That is why real use and a full day of testing never triggered it — both were quiet enough to let the probe through.

The thresholds were right the whole time. Four seconds, three missed acknowledgements, twelve to teardown: those numbers never changed and were never the problem. The clock handed to them was wrong, and no test of the policy could have caught it, because the mistake was at the call site.

A type that cannot be told about a write

The fix is one line of intent — schedule the probe from the last probe — and I did not trust myself to keep it. So the thing that owns the clocks has no way to hear about a write: 

struct LinkLiveness {
    private(set) var lastProbe: Date   // when the probe went out
    private(set) var lastAck: Date     // ATT answered a write
    private(set) var lastHeard: Date   // anything arrived at all

    mutating func probed(at t: Date) { lastProbe = t }
    mutating func acknowledged(at t: Date) { lastAck = t }
    mutating func heard(at t: Date) { lastHeard = t }
    // deliberately no wrote(at:)

    func probeIsDue(now: Date) -> Bool {
        now.timeIntervalSince(lastProbe) >= 4
    }

    func isStale(now: Date) -> Bool {
        now.timeIntervalSince(max(lastAck, lastHeard)) >= 12
    }
}

Writing more cannot make the link look healthier, because there is no method to call. The field holding the last write time is gone: after the fix it was written and never read, which is how it caused this.

In plain English: what is a watchdog here?

A timer that assumes something has died if it has not heard from it lately, and resets it. Useful when a connection can fail without announcing it. The hard part is choosing what counts as having heard from it, which is the mistake described above.

Note isStale takes the more recent of an acknowledgement and any inbound frame. That is safe in a way worth noticing: adding a second source of evidence can only make a watchdog fire less often, so it cannot bring back the failure the acknowledgement rule was written to avoid. Silence still tears nothing down. "Nothing has confirmed what the display is showing" became a separate question, surfaced to the operator and acted on by nobody.

What I'd tell you to check first

If your drops correlate with your own traffic, suspect your probe before the radio. Then check what the probe measures and what schedules it, separately — mine measured the right thing on the wrong clock, and those two faults look identical from outside.

Treat the two directions differently. Traffic proves life. Silence proves nothing, and a device can be mute for minutes while doing exactly what you asked.

Then ask whether you need the watchdog at all. Walking out of range, Core Bluetooth got there first: The connection has timed out unexpectedly, about two seconds after the last acknowledgement, against my twelve. For the common case the system beats anything you write.

What is left is a device that keeps the link open and stops working, which Core Bluetooth cannot see by definition — and which, on the evidence of that 54-second mute, an acknowledgement-based watchdog may not catch either, since the device went on acknowledging throughout.

So I kept mine and put a counter on it. Still zero after a season and it gets deleted with evidence. Ever non-zero and the question is settled the other way. That is a cheaper way to hold the argument than the two rounds I already spent having it.
